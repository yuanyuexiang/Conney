# Relay --- Automotive Supply Chain Data Hub

**项目代号：** Relay\
**项目定位：** 汽车供应链邮件数据采集与交付计划管理平台\
**版本：** v1.5\
**日期：** 2026-11-23

## 1. 项目概述

### 1.1 背景与目标

客户是一家汽车零部件制造工厂。主机厂或上游客户定期通过邮件发送交付计划
Excel。员工目前需要人工查看邮件、下载附件、打开 Excel
并整理数据，供生产计划、采购或其他业务人员处理。

Relay 自动完成邮件监控、业务邮件筛选、附件下载归档、Excel
解析、数据校验、PostgreSQL 入库、计划版本管理、差异分析和 Web
查询，为后续 ERP/MES/WMS 集成提供标准数据入口。

### 1.2 项目边界

**MVP 包含：** 邮件监控、附件下载、文件归档、Excel
解析、数据校验、数据入库、版本管理、计划差异分析、后台查询、异常重试。

**MVP 不包含：** 完整 OFTP2/AS2 EDI 通信平台；通用 EDIFACT/X12/VDA
网关；向主机厂发送 ORDRSP、DESADV 等报文；自动下达生产工单；直接修改
ERP/MES/WMS。

第一阶段准确定位是"邮件附件自动采集与供应链计划管理平台"，不是完整 EDI
交换平台。

**本期范围确认：** 不做人工调整记录，包括欠交补入、延期调配、数量手工增减、运输方式分配及其调整台账；不根据这些人工操作生成生产或发运计划。本期保留客户原始需求及其来源，按已确认规则解析、查询和比较客户计划版本。

`samples/edi/reference/德科需求.xlsx` 是 DRX 的人工处理结果，仅用于理解业务展示和物料对应关系，不作为本期自动生成报表或逐格验收的目标。该表中的包装、安全库存、运输周期及手工公式不自动成为本期计算规则。客户原始文件自带的代码、零数量、特殊记录及版本变化仍需完整保留和正确处理。

## 2. 业务流程

### 2.1 当前流程

``` text
主机厂/上游客户 -> 邮件发送 Excel -> 工厂业务邮箱
-> 员工人工下载 -> 人工查看整理 -> 生产计划/采购处理
```

### 2.2 Relay 自动化流程

``` text
业务邮箱
   |
   v
Mail Worker
   |-- 邮件规则匹配
   |-- 附件下载
   |-- 邮件/附件去重
   |-- 原始文件归档
   |
   v
Parser Worker
   |-- 文件识别
   |-- Excel 解析
   |-- 字段及业务校验
   |-- 标准化
   |
   v
PostgreSQL
   |-- 邮件、附件记录
   |-- 计划主表和明细
   |-- 历史版本
   |-- 计划变化
   |
   v
REST API / Next.js 管理后台
```

### 3.6 统一字段映射与解析规则

| 来源字段 | 内部字段/归属 | 处理要求 |
| --- | --- | --- |
| DelforNo / DeljitNo / NewTransmissionNo | 文档 `source_document_no` | 保留报文类型、传输层级和前导零 |
| PreviousDeliveryNo / PreviousDeliveryScheduleNo / OldTransmissionNo | 文档 `previous_document_no` | 仅为来源引用，不能直接认定本地上一版本 |
| New/OldDeliveryInstructionsNo 及日期 | 物料块 `customer_plan_no` / `previous_customer_plan_no` 等 | Kroschu 按物料块保存修订关系 |
| BuyerNo / SupplierNo / ShipFromNo / ShipToNo | 文档参与方；物料块保留本级地点 | 缺失保持空值，不用文件名前缀编造业务编号 |
| poNo / OrderNo / POLineNo / BlanketOrderNo | 物料块订单标识 | 字符串存储，保留订单类型 |
| BuyerItemNo / CustomerItemNo / SupplierItemNo 等 | 物料块客户/供应商物料标识 | 原始标签映射为统一字段 |
| QtyType / Qty / QtyUnit / QuantityUnit | 数量记录类型、值及单位 | 保留原始代码；未知含义不参与需求汇总 |
| DeliveryPlanStatusIndicator / DeliveryInstruction | 数量记录状态及指令代码 | 按客户、报文和模板版本解释 |
| FrequencyCode / PatternCode | 数量记录频率及模式 | 与日期粒度分别保存 |
| RequestedDeliveryDate / DateTime | `requested_delivery_date` | 合法日期点，可为空 |
| Earliest/LastDeliveryDate / HorizonStart/EndDate | 时间区间及区间角色 | 区分交付窗口与预测期间，不直接视为等价字段 |
| 接收、发运、累计数量及日期 | 物料块背景数据 | 不作为新增需求明细累计 |

通用规则：

1. 先识别模板，再按标签识别文档头、重复物料块、数量表和包装段；文件名只作辅助。标签清理换行、首尾空格及 `_x000D_`，同时保留原始标签和值。
2. 保存“文档 → 物料块 → 原始数量记录”结构，记录每个字段的 Sheet、单元格或行范围；坐标用于追溯，不作为业务身份。
3. 当前日期有 `YYYYMMDD`、`YYMMDD` 文本。六位年份采用客户确认的世纪规则，并结合文档日期校验；禁止依赖运行环境默认两位年份窗口。兼容未来真实 Excel 日期值，但不能把所有数字字符串当日期。
4. 区分空白、零数量、无日期数量、占位日期、合法日期点和区间。合法规范日期写入 `DATE`；`000000` 不写入日期列，`29991231` 保留原文并标记待确认。
5. 数量规范值使用十进制；保留原值、类型和单位。仅在数量类型语义与单位规则确认后生成可汇总需求视图；不得直接累加所有原始数量记录。
6. 必填校验按模板及记录类别执行。未知模板拒绝自动业务发布；未知代码可完成原始结构采集，标记待确认，不自动参与需求汇总或差异解释。

## 4. 功能需求

### 4.1 邮箱管理

-   客户使用 **263 企业邮箱**，首版通过 IMAP over TLS 接入；不开发 Gmail API、Microsoft Graph 或其他服务商专用接入。支持配置多个账号，首轮以指定业务邮箱完成验证。
-   收信服务器默认参考 `imap.263.net:993`，启用 TLS 并校验证书；服务器地址、端口和同步文件夹可配置，以客户管理员确认和现场连接测试为准。
-   使用完整邮箱地址登录；密码或客户端授权码按客户账号实际策略配置。上线前由管理员确认 IMAP 已开通、认证方式及访问限制。
-   邮箱连接测试、启停、同步周期配置，默认每 1～5 分钟轮询。
-   保存同步游标、上次成功同步时间和连接状态。
-   支持发件人白名单、主题关键词、收件邮箱和附件类型规则。
-   邮箱密码或客户端授权码加密保存，密钥通过部署环境注入，日志和接口响应不得输出凭据。
-   首次同步前确认历史采集起始日期及文件夹范围，避免默认扫描全部历史邮件。首版只收信，不需要 SMTP 发信权限。

不能只获取未读邮件。员工打开邮件后邮件可能变为已读，应使用 IMAP
UID/UIDVALIDITY 管理同步进度。使用只读方式和 `BODY.PEEK` 获取正文与附件，不改变已读状态，不移动或删除客户邮件。

263 官方参数参考：[客户端配置地址查询](https://download.263.net/263/helpcenter/client/20160603/970.html)、[客户端及授权方式说明](https://www.263.net/success/mail/client/20230423/1883.html)。这些参数仅作为默认参考，客户实际配置须单独验证。

### 4.2 邮件与附件管理

邮件记录邮箱、发件人、收件人、主题、Message-ID、服务商消息
ID、接收时间、附件数量、处理状态和错误信息。

首版业务解析以双方确认的 `.xlsx` 模板为准；`.xls`、`.csv` 以及 `.edi`、`.txt` 不承诺首版解析，收到时记录不支持状态并提示人工处理。扩展 `.xls` 和 `.csv` 时须分别确定解析库、编码和格式校验规则，不能假定 openpyxl 可直接覆盖所有格式。校验扩展名、实际文件格式和大小，计算
SHA-256，原始文件只读归档。记录文件名、大小、哈希、存储路径和下载时间。支持下载原件和人工重新解析。建议单附件默认上限
20 MB，可配置。

### 4.3 Excel 解析

采用 Parser Registry（解析器注册机制）。首版实现
`VitescoDelforExcelParser` 作为首条实现路径；注册机制应容纳 `DrxDelforExcelParser`、`JlrDelforExcelParser`、`JlrDeljitExcelParser` 和 `Kroschu4905ExcelParser` 五种独立规则。五种约定模板均纳入交付，Vitesco 优先跑通采集、解析和查询链路。

解析步骤：读取工作簿并识别 Sheet/模板；提取文件头；提取
Buyer、Supplier、ShipTo；循环提取物料块及块级背景数据；分类保存原始数量记录；标准化日期、数字、单位和空值；执行模板及业务校验；输出统一内部对象及待确认事项。

解析器应支持模板版本、表头定位、日期格式兼容、合并单元格处理、必填校验、明细行识别和错误单元格定位。建议使用
Python `openpyxl`。不要把所有字段硬编码为固定单元格坐标，也不要用固定块高度扫描多物料文件。结构解析结果与业务发布状态分开保存；存在未确认代码或特殊记录时，原始数据可查询，业务汇总和差异解释受规则状态约束。

### 4.4 计划管理

支持按买方、供应商、物料、计划编号、仓库、交付日期、状态、来源文件和版本查询。明细展示物料编号、描述、要求交货日期、最早/最晚交付日期、数量、单位、状态代码、数量类型代码、来源文件和版本。支持
Excel 导出，导出结果注明版本和生成时间。

后台区分原始数量记录与已确认需求视图，展示数量类型、原始代码、日期点/区间、时间角色、物料块及来源坐标。日期筛选同时支持日期点命中和区间重叠；特殊日期及无日期记录单独可查，不强制分配到某一天。汇总前明确数量口径和单位，不跨类型、跨单位或重叠预测层级直接相加。

### 4.5 版本与差异分析

每个新的有效接收事件在成功解析并通过业务校验后，按物料业务计划生成独立版本快照；同一事件的任务重试不重复生成版本。不同邮件再次发送相同内容时保留接收记录及新版本，在规则版本及比较口径相同且有可比前版时差异为 `UNCHANGED`；没有前版则建立基线。内容哈希用于文件复用，不能单独作为业务版本幂等键。变化类型建议：

-   `ADDED`：新增计划明细。
-   `CANCELLED`：仅按客户确认的显式取消、完整替换缺失行或零值规则判定，不能单凭数量为零推断。
-   `QTY_INCREASED` / `QTY_DECREASED`：数量增加/减少。
-   `DATE_CHANGED`：交付日期变化。
-   `STATUS_CHANGED`：状态代码变化。
-   `UNCHANGED`：无变化。

版本比较分为三个层级：

- 文档接收/传输版本：关联邮件、附件、来源文档编号与报文类型。
- 物料计划版本：按合作方、订单/订单行、物料、收货位置等客户确认的业务键形成版本链；Kroschu 保留每块的新旧计划编号。
- 数量记录差异：仅在相同数量语义、单位、时间角色与粒度下比较。未知类型和特殊记录仍可展示原始值变化，不输出未经确认的需求增减结论。

无稳定明细 ID 时，同一期间对比的候选键为：

`material_plan_business_key + quantity_type_code + quantity_unit + temporal_role + frequency_code + date_or_period`

`date_or_period` 使用合法日期点或起止区间，不能依赖可能全空的 `requested_delivery_date`。若同一键存在多行，不覆盖或任意选一行，需补充稳定标识或进入人工核对。

该键不能直接识别 `DATE_CHANGED`。优先使用客户确认跨版本稳定的明细标识；Vitesco 的 `LineItemNo` 仅是当前物料块标识，不能直接当作明细 ID。没有稳定标识且无法唯一匹配时，展示新增/移除候选，不猜测日期变化。

不同粒度（如周改月）、不同数量类型或 DELFOR/DELJIT 不自动逐行相减；需已确认的转换或覆盖规则。来源新旧编号仅辅助关联；迟到邮件不能按接收时间自动覆盖业务最新版本，需结合来源修订号、文档时间及客户规则判定，无法判定时标记待确认。

完整替换与增量修订语义未确认前，不把新文件缺失的行自动判为取消。零数量也不自动等于取消。版本保存完整快照；增量报文同时保留原始增量和应用规则后的快照，禁止覆盖历史。

### 4.6 异常处理

异常类型包括邮箱连接失败、邮件读取失败、附件下载失败、格式不支持、文件损坏、模板无法识别、必填字段缺失、日期/数量错误、业务校验失败和数据库写入失败。

后台展示失败阶段、错误原因、重试次数和最后错误时间，允许人工重试。重试必须幂等，不能重复生成计划和差异。

### 5.2 服务组成

采用"模块化单体 + 独立 Worker"，首版不引入 Kafka/RabbitMQ：

-   `api`：FastAPI REST 服务，供管理后台调用。
-   `mail-worker`：邮箱同步、邮件筛选和附件下载。
-   `parser-worker`：解析任务、业务校验、版本生成和差异计算。
-   `postgres`：业务数据、同步游标和任务状态。
-   `storage`：原始附件归档。

API 和 Worker 共用一个 Python 代码库和依赖锁文件、不同启动入口，不拆分为跨语言服务。Worker 通过 PostgreSQL
任务表领取任务，使用事务、行锁或租约机制避免并发重复处理。

API 首版采用同步 SQLAlchemy 会话及同步数据库驱动，阻塞调用放在同步路由或 Worker 中，避免在异步事件循环内直接执行 IMAP、工作簿解析等阻塞操作。API 不承担后台任务执行，任务入库后由 Worker 处理；首版不引入 Redis、Celery，也不依赖进程内定时任务或 FastAPI BackgroundTasks 保证持久任务完成。

Worker 使用独立数据库会话和显式事务，领取任务后释放领取事务，不在 IMAP 下载或文件解析期间长期持有数据库行锁。租约到期支持重新领取；完成写入时校验租约归属，并依靠唯一约束防止重复发布。初期以少量 Worker 进程运行，按实际积压扩容。

Python 核心规则：数量使用 `decimal.Decimal`，数据库使用 `NUMERIC`，JSON API 以十进制字符串传输数量；日期使用 `datetime.date`，带时区的事件时间统一保存为 UTC，业务日期不作时区换算。显式配置工作簿、解压和解析资源上限，不执行公式或依赖公式缓存作为业务真值。直接按单元格解析模板，首版不依赖 pandas。

Python 和各依赖的具体版本在脚手架阶段根据兼容性确定并锁定；不把未经运行验证的版本写成上线前提。

### 5.3 邮件同步策略

1.  使用配置的 TLS 参数连接 263 企业邮箱，校验证书并完成认证。
2.  只读打开指定文件夹，读取 UIDVALIDITY；同步状态按账号和文件夹分别保存。
3.  根据 UID 游标获取新邮件，使用 `BODY.PEEK` 读取所需内容，不依赖未读标记。
4.  应用筛选规则，持久化邮件记录和符合规则的附件采集任务。
5.  仅在本批邮件均已记录或持久化为可重试任务后推进游标；不得因后续邮件成功而跳过尚未落库的失败邮件。
6.  Worker 下载附件、计算哈希并可靠归档，再保存邮件附件关联和解析任务。失败独立重试；原件未可靠保存前不标记下载成功。

连接断开后指数退避重连。UIDVALIDITY 变化时暂停沿用旧游标，在已确认的历史范围内重新扫描，并通过来源记录、Message-ID 和内容哈希辅助核对；Message-ID 不保证存在或唯一，不能独立作为去重依据。文件夹移动或重新扫描产生的不确定重复进入核对流程，避免直接生成重复业务版本。

首次连接验证应覆盖 TLS、认证、文件夹访问、附件读取及网络访问限制；记录诊断结果，不记录密码或授权码。

## 6. 数据库设计

### 6.1 核心表

  表名                 用途
  -------------------- --------------------------

  `edi_document_blocks` 物料块、块级修订和背景数据

  `edi_partners`       买方、供应商等参与方
  `edi_materials`      物料主数据
  `edi_plans`          每个物料业务计划的版本快照
  `edi_plan_items`     快照内数量明细及来源记录引用

  `processing_jobs`    邮件和附件处理任务
  `audit_logs`         用户操作和审计日志

### 6.2 关键设计原则

-   原始邮件/附件、解析文档、业务计划分层保存。
-   IMAP 邮件按账号 + 文件夹 + UIDVALIDITY + UID 唯一标识；Message-ID 作为辅助追溯信息。
-   附件接收记录按邮件记录 + MIME 部件标识唯一；底层文件内容可按 SHA-256 复用，但每次接收关系必须保留。
-   计划版本不可变，禁止覆盖历史快照。
-   数量使用 `NUMERIC`，不要使用浮点数。
-   业务编号按字符串保存，避免前导零丢失。
-   合法业务日期使用 `DATE`；同时保存原始日期、解析状态及世纪解释规则。特殊值不强制转换。
-   文档、物料块和数量记录分层；数量记录不强制具备交货日期。零、空值和特殊记录不可合并。
-   单位、数量语义、时间角色和粒度为比较及汇总前提，默认不做跨口径累计。
-   计划明细关联来源文档和版本。
-   数据写入与任务状态更新放在事务中。
-   为常用查询字段建立索引。

### 6.3 关键字段建议

- `edi_documents`：`id`、`attachment_id`、`message_type`、`source_document_no`、`previous_document_no`、`document_type_code`、`message_function_code`、`document_created_at`、`raw_header_data`、`business_review_status`。
- `edi_parse_runs`：`id`、`document_id`、`parser_name`、`parser_version`、`mapping_version`、`status`、`diagnostics`、`created_at`。同一文档可多次解析，结果不可原位覆盖。
- `edi_document_blocks`：`id`、`parse_run_id`、`block_index`、`source_block_ref`、`buyer_item_code`、`supplier_item_code`、`order_no`、`order_line_no`、`customer_plan_no`、`previous_customer_plan_no`、新旧计划日期、工厂/收货方/仓库/卸货点、`raw_background_data`。缺失合作方编号保持空值，文件识别模板与业务合作方映射分开处理。
- `edi_quantity_records`：`id`、`block_id`、`record_class`（待分类、需求、累计、特殊等）、`quantity_type_code`、`quantity_raw`、`quantity`、`quantity_unit`、`schedule_status_code`、`delivery_instruction_code`、`frequency_code`、`pattern_code`、`temporal_kind`（日期点、区间、无日期、特殊）、`temporal_role`（交付窗口、预测期间等）、`requested_delivery_date`、`period_start`、`period_end`、`raw_date_values`、`validation_status`、`source_cells`、`raw_row_data`。类别由版本化业务规则确定，不由数字大小推断。
- `edi_plans`：`id`、`business_key`、`customer_plan_no`、`version_no`、`source_document_id`、`source_block_id`、`parse_run_id`、`business_rule_version`、`supersedes_plan_id`、`publication_status`、`created_at`。本地版本号与客户修订号分开保存。
- `edi_plan_items`：`id`、`plan_id`、`source_quantity_record_id`、`stable_line_id`（可空）、规范数量/单位/类型、日期点或区间、状态及时间粒度。完整保留快照，不强制用日期点代表区间。
- `edi_plan_changes`：`id`、`old_plan_id`、`new_plan_id`、`change_type`、`business_key`、新旧明细引用、数量及差额、新旧日期点/区间、`match_basis`、`review_status`。

`source_cells` 保存 Sheet 名和单元格/行范围；原件、解析批次、物料块、数量记录、快照与差异必须可追溯。物料计划幂等约束为接收文档 + 来源块标识，数据库唯一约束与事务共同防止重试重复发布。

重新解析生成新的 `edi_parse_runs` 及其块/记录，不改变已发布快照。规则修正后如需替换当前业务结果，必须通过明确的审核发布操作保留旧快照和更正关系；不得伪装为新邮件接收事件。

实际字段以客户实施规范确认后调整。

## 8. REST API 规划

统一前缀 `/api/v1`，FastAPI 生成 OpenAPI 契约。按业务域组织路由：

| 资源 | 示例接口 | 行为 |
| --- | --- | --- |
| 邮箱 | `GET/POST /mail-accounts`、`PATCH /mail-accounts/{id}` | 查询、创建和修改配置，响应不包含凭据 |
| 邮箱任务 | `POST /mail-accounts/{id}/connection-tests`、`POST /mail-accounts/{id}/sync-jobs` | 创建连接测试或同步任务 |
| 邮件 | `GET /mail-messages`、`GET /mail-messages/{id}` | 邮件列表与详情 |
| 附件 | `GET /attachments`、`GET /attachments/{id}/download` | 查询及鉴权下载原件 |
| 文档 | `GET /documents`、`GET /documents/{id}/blocks`、`GET /documents/{id}/parse-runs` | 文档、物料块与解析历史 |
| 原始数量 | `GET /document-blocks/{id}/quantity-records` | 数量类型、规范值、原值及来源坐标 |
| 重新解析 | `POST /documents/{id}/parse-jobs` | 入队解析，不直接改写已发布计划 |
| 计划 | `GET /delivery-plans`、`GET /delivery-plans/{id}/items` | 计划查询及快照明细 |
| 版本与差异 | `GET /delivery-plans/{id}/versions`、`GET /delivery-plans/{id}/changes` | 同业务计划版本链及差异 |
| 模板与任务 | `GET /parser-templates`、`GET /jobs/{id}` | 模板元数据及任务进度 |

查询用 GET，创建任务用 POST，修改配置用 PATCH。列表统一支持分页、排序和筛选；错误响应含稳定错误代码、说明及可用的字段/来源坐标。文档查询不暴露密码、授权码或内部文件路径。

连接测试、邮件同步、文件解析等耗时操作创建持久化任务后返回 `202 Accepted` 和任务 ID；前端通过 `/jobs/{id}` 查询状态。日期字段允许为空，日期点和区间分开表示，并暴露时间角色、原始代码、业务确认状态。数量使用字符串表示，禁止由客户端浮点转换造成精度损失；接口不得将未确认数量自动汇总为需求。

接口先满足管理后台及本期查询需求；外部 ERP/MES 接入仍为后续范围，不因 REST 选型自动纳入。

## 9. 安全、可靠性与运维

### 9.1 邮件和附件安全

-   只处理白名单邮箱和允许的附件类型。
-   校验扩展名、MIME 和文件签名，不信任邮件声明的文件类型。
-   限制文件大小、Sheet 数量、行列数和解析耗时。
-   禁止执行宏，不自动访问 Excel 外部链接。
-   原始附件隔离存储，下载必须鉴权。
-   根据客户环境增加杀毒扫描。
-   防范压缩炸弹、恶意公式和异常工作簿。

### 9.2 幂等与可靠性

-   邮件唯一键：邮箱账号 + 文件夹 + UIDVALIDITY + UID。
-   附件接收唯一键：邮件记录 + MIME 部件标识；SHA-256 仅用于底层文件去重。
-   解析任务使用状态机：`PENDING`、`PROCESSING`、`SUCCEEDED`、`FAILED`。
-   任务领取使用数据库事务、行锁或租约，避免多 Worker 重复执行。
-   失败采用有限次数重试和指数退避。
-   解析和计划写入使用事务。
-   计划接收幂等键由附件接收记录 + 来源物料块标识组成；规则版本另行记录，不用于绕过去重。重试及人工重新解析不得新增接收版本，规则更正通过明确的审核发布流程留存审计。
-   原始文件与解析记录永久关联，支持追溯。

### 9.3 备份与监控

-   PostgreSQL 定期备份并验证恢复。
-   附件存储纳入备份策略。
-   记录邮件同步延迟、解析耗时、失败率、任务积压和存储容量。
-   对邮箱连接失败、连续解析失败、任务积压和磁盘空间不足告警。
-   记录关键操作审计日志。

配置通过环境变量加载并校验；`.env.example` 仅存字段说明和无敏感占位值，实际凭据不入库到源码。CI 安装锁定依赖后执行格式、静态检查、测试及构建；前端命令随 `web/package.json` 确定。


## 11. 实施阶段与验收标准

### 阶段一：需求确认与样本固化

-   邮箱服务商已确认为 263 企业邮箱；确认 IMAP 服务地址、TLS 端口、账号数量、密码/授权码方式、文件夹、历史起始日期及访问限制，并完成实连验证。
-   在已有五份样本基础上，为每种拟验收模板补齐同一业务计划的连续两版、异常及格式变体样本；不能只以总文件数量替代覆盖要求。
-   当前 `samples/edi/raw/` 已有 Vitesco、DRX、JLR、Kroschu 的五份样本，包含 DELFOR 和 DELJIT；逐份建立模板清单。本期覆盖五种约定模板，实施顺序及当前进度见[工作地图](../工作地图.md)。
-   获取客户 EDI 实施指南。
-   确认各模板代码、数量口径、特殊日期、计划版本、替换/增量规则和业务匹配键；明确 DELFOR/DELJIT 的关系。
-   固化字段映射和解析测试样本。

**交付物：** 需求确认表、字段映射表、样本文件集、解析规则说明。

### 阶段二：邮件采集

-   完成邮箱配置、连接测试和增量同步。
-   下载附件、哈希去重、原始文件归档。
-   保存邮件和附件记录。
-   支持断线重连和同步续跑。

**验收：**
测试邮件能自动发现；附件完整下载；重复同步不产生重复附件业务记录；员工将邮件标记为已读不影响采集，采集不改变邮件已读状态；单封邮件失败后其他邮件可继续处理且失败任务不丢失。

### 阶段三：Excel 解析与入库

-   实现 Vitesco DELFOR Excel 解析器。
-   提取文件头、参与方、全部物料块及原始数量记录，保存坐标和解析规则版本。
-   其余四种约定模板分别实现解析器；未知数量类型先保留并标记，不直接作为需求汇总。
-   完成结构校验和业务校验。
-   保存解析结果和原始文件关联。

**验收：**
对双方确认的样本文件，字段、物料块数及数量记录数符合第 12 节基线；区间、零数量及特殊记录不丢失；异常有明确坐标；重新解析保留历史且不重复发布业务版本。

### 阶段四：版本与差异分析

-   生成计划版本快照。
-   确认业务匹配键。
-   计算新增、取消、数量和日期变化。
-   展示历史版本和差异明细。

**验收：**
对每种纳入范围的模板，使用同一业务计划的连续版本，按已确认数量口径与业务人员逐项核对；覆盖无变化、增减、取消、区间变化和迟到版本。当前 JLR DELFOR/DELJIT 不作为连续版本对；缺少版本样本或规则时，该模板的业务差异验收保持待完成。

本期验收只核对原始附件字段、客户计划版本及已确认的差异规则，不要求结果与“德科需求.xlsx”中的人工调整后数量一致。

### 阶段五：管理后台与上线

-   完成概览、邮件、附件、计划、差异和配置页面。
-   完成权限、日志、备份、监控和部署。
-   在客户环境试运行并处理异常。

**验收：**
业务人员可独立查询邮件、下载原件、查看计划和差异；系统重启后可恢复同步；关键数据可备份和恢复。

## 12. 测试方案

后端采用 pytest；纯解析与领域规则测试不依赖网络，数据库事务、唯一约束、任务租约和迁移使用独立测试 PostgreSQL 验证，不以 SQLite 替代这些语义。API 测试覆盖权限、分页、错误契约、数量字符串及任务入队；IMAP 先用可控替身覆盖失败路径，再以客户授权账号完成 263 环境实测。

-   邮件测试：新邮件、已读邮件、重复邮件、无附件邮件、多附件邮件、异常发件人。
-   附件测试：正常
    xlsx、损坏文件、伪装扩展名、超大文件、重复附件，以及 xls/csv 等未支持格式的明确拒绝。
-   解析测试：必填字段缺失、日期格式变化、空数量、零数量、多个
    Sheet、模板列变化。
-   版本测试：新计划、完全相同计划、数量变化、日期变化、计划撤销、重复修订。
-   可靠性测试：邮箱断网、数据库短暂不可用、Worker 重启、任务重复领取、UIDVALIDITY 变化、下载失败后的游标推进与续跑。
-   263 接入测试：认证失败、授权码失效、文件夹访问限制、首次历史范围、只读采集，以及已读邮件采集。
-   安全测试：未授权下载、恶意工作簿、异常压缩文件、凭据日志泄漏。

### 12.1 样本结构回归基线

| 模板 | 物料块数 | 原始数量记录数 | 必须断言的特征 |
| --- | ---: | ---: | --- |
| Vitesco DELFOR | 1 | 88 | 19 个零值；88 个区间；指定日期全空；MessageFunction 为空，PreviousDeliveryNo 为 23 |
| DRX DELFOR | 13 | 309 | 数量类型 1/83 为 299/10；日期点/区间为 129/180；块长不同 |
| JLR DELFOR | 1 | 37 | 数量类型 1/3 为 5/32；日/周/月为 5/18/14 |
| JLR DELJIT | 1 | 11 | 类型 12/79/119 各 1 条，3/1 各 4 条；2 条无交货日期；同日多类型不合并 |
| Kroschu 4905 | 40 | 190 | 40 条特殊日期、150 条正常日期记录；每块修订及单位 ST 保留 |

五份均保留为解析架构的目标测试集；尚未实现或验证的解析器状态见[工作地图](../工作地图.md)。当前数量基线只能验证结构，不能证明代码含义或业务计算正确。

### 12.2 边界与语义测试

- 六位年份规则、八位日期、真实 Excel 日期值、跨年区间、`000000`、`29991231`、空白与非法日期分别测试。
- 文字编号前导零、空格、换行、`_x000D_`、已有乱码、合并单元格和标签别名均保留原始来源。
- 同日期不同数量类型、累计与单期数量、不同单位、周/月重叠、未知代码不直接相加或转换。
- 多物料块长度变化、块缺失、重复业务键、包装段干扰、文档级与块级地点不同均需检测。
- 零数量不默认取消，特殊尾部记录不当成交货行；未知语义不触发自动业务发布或差异解释。
- 同一任务重试、相同内容不同邮件、规则更新重解析、迟到版本、不同报文/物料误配分别验证幂等与追溯。

解析测试建立 Golden Files（标准样本集），预期 JSON 包含文档头、全部物料块、全部原始数量记录、规范值、特殊记录和来源坐标。预期结果需人工核对；业务分类和汇总另以客户确认规则测试，不用程序输出反向充当预期。测试副本如需脱敏，保留结构与数据类型，原件不改写。

## 14. 风险与待决策事项

  风险/问题            影响               处理建议
  -------------------- ------------------ -----------------------------------
  Excel 模板变化       解析失败           模板版本化、样本回归测试
  邮箱协议或授权限制   无法稳定采集       尽早确认邮箱服务商和管理员权限
  计划替换规则不清楚   版本和差异错误     获取实施指南并由业务确认
  计划编号不唯一       错误合并计划       定义完整业务匹配键
  代码含义未确认       误判承诺需求       原始代码入库、规则配置化
  累计与单期混用       需求重复计算       按数量语义和单位限制汇总
  日期点与区间混用     丢行或错误匹配     保存时间角色与粒度
  多物料块版本混用     覆盖错误计划       按物料业务键维护版本链
  缺少连续版本样本     差异无法验收       补齐同计划连续版本并人工核对
  附件恶意或损坏       安全与稳定性风险   文件隔离、格式检查、大小限制
  后续系统接口不明确   集成返工           首版建立稳定 Canonical Data Model

上线前必须确认：263 邮箱接入参数及权限、真实模板数量、客户实施指南、版本替换语义、计划业务匹配键、数据保留期限、部署位置和备份责任。

## 15. MVP 完成定义

满足以下条件即可认为第一阶段交付：

1.  指定邮箱可稳定自动同步。
2.  符合规则的 Excel 附件可自动下载并归档。
3.  邮件和附件重复处理不会造成重复业务数据。
4.  纳入范围的模板按基线提取全部物料块和原始数量记录；待确认代码和特殊日期明确标记，不丢弃、不误汇总。
5.  解析结果和原始附件可以相互追溯。
6.  每个有效计划接收事件保留独立版本，同一事件重试不重复生成版本。
7.  已确认规则的物料计划版本以真实连续样本验证差异；日期区间及不同数量类型正确区分，无法唯一匹配的结果显式待核对。
8.  失败任务可定位、重试和审计。
9.  管理后台能够查询邮件、附件、计划和变化。
10. Docker Compose 可部署，备份和恢复流程经过验证。
